0. What this document is

A complete, implementation-ready blueprint for the Sarthak Arts e-commerce platform: a premium, single-seller D2C store selling handcrafted Vastu Shastra instruments (copper, brass, silver pieces set with a single gemstone each), selling to both Indian and international customers. It covers architecture, data model, design system, every customer-facing page, every admin/seller screen, the platform's bespoke consultation booking system, the full order/returns/reviews lifecycles, SEO, legal pages, testing strategy, infrastructure, and a phased build roadmap.

This document assumes the reader has not seen the brainstorming conversation that produced it — every decision is stated with its reasoning, not just its conclusion. Every page and screen described in Sections 7 and 8 has its actual visual mockup embedded directly beneath its description — there is nothing to click through to elsewhere.

1. The one rule that governs everything

Nothing is hardcoded. Every layer — frontend, backend, database — is modular, configurable, and evolvable without ever requiring a rebuild or a restart-from-scratch.

This is not a nice-to-have; it is the primary architectural constraint on this project, stated explicitly by the business owner and treated as a hard gate on every decision in this document. Concretely:

  • Anything that is a business decision (a direction's name, a metal's rate, a role's permissions, a shipping zone, a discount type, a payment gateway) lives as data in the database, editable from the admin panel.
  • Anything that is a structural/technical decision (how the database is normalized, which framework renders a page) lives in code — but is written so business decisions never leak into it as literals.
  • The test applied to every design choice below: "If this needs to change in six months, does it require a rebuild, or just a configuration/data change?" If the answer is "rebuild," the design was rejected and redone.
  • This governs every table, every screen, every integration described below, and continues to govern the project after launch.

3. Architecture & tech stack

Chosen approach: a unified Next.js monolith, evaluated against two alternatives (separate frontend/backend services, and a headless-commerce engine like Medusa.js) and preferred because:

  • Three distinct user-facing surfaces (customer storefront, admin panel, consultant portal) need one coherent data model and auth system — a monolith keeps type-safety and auth logic shared, not duplicated across a network boundary.
  • The consultation booking system doesn't map onto any off-the-shelf commerce engine's built-in models — it would be built custom regardless.
  • At this scale (medium catalog, single seller), a separate backend service is meaningfully more operational complexity for no present benefit.

Applying the modularity rule to this layer

  • Directions, metals, gemstones, categories, purposes → reference tables, not enums in code.
  • RBAC roles/permissions → tables with a join table, not a switch statement.
  • Payment gateway routing, currencies, shipping zones, tax rules → config records evaluated by a generic rules engine. Adding a third gateway or a new currency later is a data operation.
  • Notification triggers → an event-rule table (event type → template → channel).

4.2 Core commerce entities

  • products — name, slug, description, category_id, status, SEO fields
  • product_variants — actual sellable SKUs; every product has at least one default variant
  • product_composition — the heart of the honest-materials copy and the certificate generator: metal, weight, gemstone per line item. Supports any number of line items. Purely descriptive — has no connection to pricing.
  • product_price_history — a simple log of the admin's own price changes (old price, new price, changed_by, changed_at) — kept for the admin's own reference, not tied to any automated calculation
  • product_directions — join table (a product can map to more than one zone)
  • product_images — ordered, with required alt text
  • carts / cart_items — persisted per user or guest session
  • orders / order_items / order_status_history — status from order_statuses, never hardcoded; orders record which currency was actually paid
  • order_certificates — generated PDF reference, snapshotted composition data
  • return_requests — order_id, reason, status, timestamps
  • addresses, payments, reviews, coupons, gift_options — standard commerce entities, each structured for extensibility (e.g. coupon rules as structured JSON so new discount shapes need no schema change; addresses support international formats)

4.3 Consultation booking entities

Built generically around consultation types, not hardcoded to Vastu — this is what lets astrology slot in as a second type today, and any future type slot in the same way.

  • consultation_types — Vastu Placement and Astrology at launch; each has its own duration, fee, and whether it credits toward an order. A reference table, editable from Settings.
  • consultants — linked to a user account holding the Consultant role. One row per consultant, schema supports N.
  • consultant_consultation_types — join table: which type(s) a consultant offers — one, or both.
  • consultant_availability — recurring + one-off slots, owned by the consultant directly. One calendar per consultant, regardless of how many types they offer.
  • bookings — consultant, consultation_type, customer, slot, status, video-link, linked order (the order-credit rule is per-type, via consultation_types.credits_toward_order)

4.4–4.6 Content, social, identity

  • content_blocks — powers every owner-editable editorial and legal page
  • social_accounts / social_posts — source field (manual/synced) allows admin-curated launch, live-sync upgrade later
  • users / user_roles — one person can hold multiple roles (e.g. Admin + Consultant); guest checkout links a lightweight guest record that upgrades on signup
  • No seller_id/tenant isolation anywhere — single-seller; adding it later is an additive migration, not a rebuild

5. Design system

The visual language fuses three structural concepts researched and workshopped during design review — not a flat palette, but four layers, each governing a different part of the system, so the pieces compose instead of competing.

5.1 The four layers

  • Foundation — warm parchment ground, ink-brown text, brass linework. Ledger-honest, not stark.
  • Space (Brahmasthan principle — a home's sacred center stays open, not filled) — every page protects one dominant focal object and a deliberately empty center.
  • Navigation (Mandala Interface) — the 8-direction Vastu Purusha Mandala wheel is the literal, functional "Shop by Direction" filter, rendered on a rare dark charcoal panel reserved only for this and the hero glyph.
  • Motif + dynamic color (Smith's Hand) — a recurring design → shape → set → certify process line-art motif; accent color is never arbitrary, always the real gemstone/direction color resolved from data.

5.3 Typography & component rules

  • Display serif for headlines (production candidate: Fraunces); humanist sans for UI/body (Inter); tabular ledger numerals for weights/prices/dates.
  • The mandala wheel is one reusable component, wedge count read from live directions data (8 today, not hardcoded).

7. Customer storefront — every page, with mockup

Every page below shows its actual rendered mockup directly beneath its description, in the approved design system.

7.1 The certificate of composition — how it's actually produced

Every order ships with a certificate stating exact metal weight and gemstone. Mechanism: at order confirmation, the system snapshots that product's current product_composition into order_certificates (so a later product edit never retroactively rewrites an issued certificate) → a PDF is generated server-side, styled with the same design tokens as the site → stored in R2 → attached to the confirmation email and re-downloadable from Account → Orders. Fully automatic, no manual admin step.

7.2 Returns — the customer-facing side

From Account → Orders, within the configured return window, the customer opens the return flow, selects a reason from the admin-editable return_reasons list, adds a note, and submits — creating a return_requests row. Status updates flow through Requested → Approved → Refunded (or Rejected, with a visible reason). Engraved/personalized pieces are excluded automatically via a products.is_final_sale flag.

7.3 The 2-minute home audit — what it actually is

Referenced in the homepage hero copy but never specified until this document. Design: a short guided quiz at /home-audit — plain-language questions (entrance direction, kitchen direction, whether the layout is standard or irregular), each question and answer-mapping stored in audit_questions/audit_answer_rules so the quiz itself is fully admin-editable, not a hardcoded wizard. Irregular-layout answers surface the consultation booking CTA, reusing the copy's own existing "Do I need a consultation?" logic. Needs owner confirmation on the exact question set (Section 14).

7.4 Guest checkout

Checkout allows completing a purchase without an account. After a successful guest order, the confirmation page offers one-click account creation from the details already entered. Recommended as a premium-checkout default, not explicitly requested — flagged for confirmation in Section 14.

7.5 SEO & discoverability

Dynamic meta tags per product (falling back to the copy doc's own template pattern when left blank); JSON-LD structured data (Product, Review/AggregateRating, BreadcrumbList, FAQPage); auto-generated XML sitemap; canonical URLs on filtered views; required alt text on every product image; Core Web Vitals addressed structurally via the SSR/ISR architecture already chosen.

7.6 Legal & policy pages

Terms of Service, Privacy Policy, and Shipping & Returns — referenced by the footer nav but undesigned until now. All three are content_blocks-backed, owner-editable from the same CMS screen as every other editorial page.

7.7 Gifting — minimal launch scope

The footer lists "Gifting" with no further detail in the source copy. Minimal Phase 2 scope: an is_gift flag + gift note field at checkout. A full gift-registry/gift-card system is explicitly out of scope unless the owner asks for more (Section 14).

9. Core intelligent systems — full working

9.1 Pricing — fully manual, by design

There is no pricing engine, no live metal-rate feed, and no automated price computation anywhere in this platform — a deliberate business decision, not a deferred feature.

  1. The admin fills in a plain base_price field directly, in their chosen base currency, when creating or editing a product.
  2. product_composition (the metal/gemstone breakdown) is entered separately and used only for the material-honesty promise and the certificate — it has no computational link to the price field.
  3. International pricing: the storefront converts and displays the admin's entered price into the shopper's local currency at the current exchange rate — a display step, not a pricing decision. The admin can also set an explicit override price per currency for a cleaner number (e.g. a flat $199 instead of a converted $198.73).
  4. Every price change is logged to product_price_history for the admin's own reference — not shown to customers.
  5. There's nothing to keep confidential here beyond ordinary business practice — with no formula, rate feed, or suggestion mechanism, there's no computed cost/margin data anywhere in the system to leak.

9.2 The consultation booking system, end to end

  1. Customer opens /consultation and first picks a type — Vastu placement or astrology — read from consultation_types, so a third type appears here automatically once added.
  2. Within that type: if it has one consultant, it skips straight to date/slot selection; if several, a picker step appears.
  3. Available slots computed from that consultant's availability minus already-booked slots.
  4. Customer pays that type's consultation fee via Razorpay or Stripe depending on their location; a bookings row is created with the chosen type.
  5. The consultant (own login) sees and manages the booking and their availability directly — one calendar, even if they offer both types.
  6. A video/call link is sent via email/SMS at booking time.
  7. On completion: if that type has the order-credit rule enabled, the customer's account carries a credit flag — an order over ₹15,000 (or the equivalent) applies the fee as a discount, enforced by bookings.linked_order. Whether astrology should carry the same credit/fee/duration as Vastu is a business decision (Section 14).
  8. The reverse direction also works — the big-order gift. Any order crossing the configured threshold (₹15,000 at launch) automatically grants that customer one free Vastu placement consultation (a consultation_entitlements row), exactly as the announcement bar promises — bookable through the normal flow at ₹0. Threshold, granted type, and on/off are admin settings.

9.4 Search, end to end

Product search and direction/category/purpose filters query the same underlying tables via Postgres full-text search at launch, behind a small abstraction so a future swap to Meilisearch/Algolia is a backend change, not a rewrite of every calling page.

9.5 The core commerce data flow — browse to fulfillment

  1. Browse — read-only, from products/composition/reference tables.
  2. Add to cart — a cart_items row, linked to user or guest session.
  3. Checkout begins — shipping cost and tax resolved from config tables by address zone, not hardcoded math; coupons applied if entered.
  4. Payment — gateway chosen automatically by destination (Razorpay for India, Stripe for international). On success: orders/order_items created from server-held cart state (never client-submitted, preventing price tampering), status logged Confirmed, certificate generated, notifications fire, cart cleared. No internal payout engine needed — single-seller means both gateways settle directly to the business's own bank account(s).
  5. Fulfillment — admin updates status Packed → Shipped (tracking captured) → Delivered.
  6. Post-delivery — return window opens; customer may review or request a return within it.

9.6 Returns & refunds, end to end

Customer submits a request (excluded automatically for final-sale items) → admin approves/rejects on the returns queue, with a visible reason either way → if approved, pickup/drop-off arranged → on confirmed receipt, refund triggered via the original gateway's refund API (Razorpay or Stripe, whichever was used) back to the original payment method, in the original currency → order history reflects the full journey, one continuous auditable record.

9.7 Reviews & moderation, end to end

A review can only be submitted against a Delivered order — verified_purchase is set automatically, there is no unverified path. Defaults to published (configurable to require approval). Admin can hide any review or reply, both from the review moderation screen and surfaced as a dashboard alert when new and unreplied.

10. Payments, auth & security

  • Payments: Razorpay and Stripe both live at launch — Razorpay for India, Stripe for international. Gateway selection is a config lookup by destination, not a hardcoded conditional.
  • Auth: custom session-based; customers get social login + OTP + guest checkout; staff get email+password with mandatory MFA. HttpOnly, secure cookies with refresh-token rotation.
  • RBAC: roles/permissions tables checked via route-group middleware; a user can hold multiple roles at once.
  • Data protection: TLS everywhere, encryption at rest, parameterized queries (no raw SQL interpolation), CSRF protection, rate limiting on auth endpoints.
  • Audit trail: price history, order-status, return, and content-edit history are all permanent, append-only records.
  • Order integrity: orders are always built server-side from database state at payment confirmation, never trusting client-submitted prices.

No pricing engine, so nothing to protect there: since the admin sets every price manually and there's no formula, rate feed, or suggestion mechanism anywhere in the system, there's no computed pricing/cost data that could leak to a customer even by accident. What customers see is exactly what any store shows — the material composition (metal type, exact weight, gemstone, the "full material transparency" trust feature) and the final selling price. The admin's own reasoning for a price lives entirely outside the system, the same as it would for any manually-priced store.

11. Infrastructure & DevOps

  • Hosting: Vercel (auto-scaling, edge-cached storefront via ISR).
  • Database: Neon/Supabase Postgres, branch-per-environment so schema changes are tested before touching live data.
  • Storage: Cloudflare R2 + CDN.
  • CI/CD: lint → typecheck → test → deploy, staging as a mandatory gate for schema-affecting changes.
  • Monitoring: error tracking + uptime checks from day one, given the owner has no engineering team to notice an outage manually.
  • Backups: automated daily Postgres backups, retained on a rolling window.

13. Phased roadmap

Structured to be timeline-agnostic — each phase is a complete, shippable state, not a partial one. Every phase boundary was checked against the modularity rule: none require a rebuild of a prior phase.

Phase 1 — MVP

  • Storefront core (homepage, direction wheel, PLP, PDP, cart, checkout with both gateways + guest, account/orders), certificate generation, consultation booking for both launch types (Vastu placement, astrology).
  • Admin: dashboard, products with manual price entry, orders, basic settings including currency/gateway configuration.
  • Content pages shipped with real copy; CMS editing deferred to Phase 2.
  • Core notifications, SEO foundation, unit + E2E coverage for checkout (both gateways) and order logic.

Phase 2 — Core differentiators

  • CMS editor for editorial + legal content.
  • Returns/refunds workflow (both gateways); review submission + moderation; the home audit tool.
  • Bulk product tooling; analytics incl. direction-wise and market-wise (India vs. international) sales; social content module; gifting (minimal scope).
  • Full notification set; newsletter integration; per-currency price overrides if live conversion isn't precise enough.

Phase 3 — Further expansion

  • Additional international markets/currencies beyond the initial launch set, as demand shows up.
  • A second consultant for either type, or a third consultation type entirely; live social API sync; search backend swap if scale warrants; granular RBAC roles; native app only if usage data justifies it.
